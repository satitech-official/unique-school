Executive Summary
This document presents a structured troubleshooting methodology for three related hosting incidents: an 
inaccessible cPanel interface, an unavailable SnappyMail webmail application, and selected subdomains that fail 
while the main domain remains reachable. The methodology starts by defining the user-visible symptom, 
separating local service health from remote reachability, collecting time-correlated evidence, testing each layer 
independently, and applying a controlled resolution only after the failing layer has been identified.
The central principle is that a symptom is not a root cause. For example, “cPanel is down” may actually mean that 
the cPanel application server is stopped, TCP port 2083 is blocked, the hostname resolves to the wrong address, 
a TLS certificate causes browser rejection, the server is resource-starved, or only the client network is blocked. 
Likewise, “webmail is not working” must be divided into web-interface failure, authentication failure, IMAP retrieval 
failure, SMTP submission failure, and mail-delivery failure.
Technical Accuracy Note
Native cPanel, WHM, and cPanel Webmail interfaces are 
served by the cPanel Server Daemon (cpsrvd), not by the 
hosted Apache virtual host. Apache or Nginx failures can 
still affect proxy/service-subdomain access or a separately 
installed SnappyMail instance, but they are not automatically 
the direct cause of https://hostname:2083 failures.
Because the scenario provides no live command output, this report does not pretend that one exact root cause 
has already been proven. Instead, it provides a decision-oriented runbook and an illustrative final RCA for each 
issue. In an actual incident, the final RCA must be supported by timestamps, command output, logs, configuration 
diffs, and validation results.

1. Introduction
1.1 What Technical Support Means in a Server Environment
Technical support in a hosting environment is the controlled process of restoring a service while protecting data, 
security, availability, and auditability. The engineer must translate a user report into testable technical statements, 
determine the affected scope, reproduce or observe the failure, isolate the failing layer, apply a low-risk 
correction, and prove that the service is stable after recovery.
A professional support engineer does not begin by restarting every service. Blind restarts may temporarily hide 
the evidence, create additional downtime, or make the original cause impossible to prove. The preferred 
sequence is: record the time and error, test locally and remotely, check service state and resource health, review 
relevant logs, validate configuration syntax, then restart only the affected component if the evidence supports it.
1.2 Linux Server Administration
Linux server administration covers operating-system health, service management, networking, storage, 
permissions, identity, security controls, package maintenance, logging, backups, and application configuration. 
On a cPanel server, the administrator must also understand the cPanel service layer, account metadata, DNS 
zones, Apache user-data files, Exim and Dovecot integration, AutoSSL, and the effect of third-party components 
such as Nginx reverse proxies, CSF, Cloudflare, or an independently deployed webmail application.
1.3 Why a Troubleshooting Methodology Matters
 It prevents random changes and reduces mean time to recovery.
 It separates correlation from causation and preserves incident evidence.
 It makes actions repeatable for other engineers and future incidents.
 It reduces the risk of fixing one service while breaking another.
 It produces an auditable RCA, including what failed, why it failed, and how recurrence will be prevented.
1.4 Root Cause Analysis (RCA)
Root Cause Analysis identifies the underlying condition that allowed the incident to occur. A complete RCA 
includes the triggering event, technical failure mechanism, contributing conditions, detection gap, impact, recovery 
action, and preventive control. For example, “Dovecot was restarted” is a recovery action; “Dovecot stopped 
because /var was full after log rotation failed, and monitoring had no inode alert” is an RCA.
1.5 Troubleshooting Principles Used in This Report
Principle Application
Scope before action Determine whether the failure affects one user, one domain, 
one protocol, or the entire server.
Local before remote Test loopback/origin access first, then firewall, DNS, proxy, and 
client network.
Layer isolation Treat application, service, port, firewall, DNS, TLS, and client 
layers independently.
Time correlation Match the user’s failure time with logs, service transitions, 
resource spikes, and configuration changes.
Reversible change Back up configuration and prefer a minimal fix that can be rolled 
back.
Validation Verify from both the server and an external client; test the actual 
user workflow.

3. Issue 1 - cPanel Is Not Accessible
3.1 Problem Description and Symptoms
The client cannot open cPanel using a secure URL such as https://hostname.example:2083 or a service 
subdomain such as https://cpanel.example.com. The main website may or may not remain available. The 
reported symptom must be refined into a specific failure mode.
Observed Symptom Likely Layer
Connection timed out Routing, firewall, security group, blocked source IP, or no 
listener
Connection refused No process listening, service stopped, or local reject rule
TLS/certificate warning Hostname mismatch, expired certificate, incomplete chain, old 
client protocol, or wrong endpoint
HTTP 500 / blank interface cpsrvd application error, corrupted package, Perl/module error, 
permission issue, or full filesystem
Login page opens but credentials fail Authentication, account status, brute-force protection, clock 
skew, or user error
Works on server but not externally Firewall, NAT, provider security group, Cloudflare/proxy, ISP, or 
source-IP block
Works by IP but not hostname DNS record, resolver cache, hosts file, or hostname certificate 
problem
3.2 Possible Root Causes
Potential Cause Technical Explanation
cpsrvd/cPanel service down The cPanel Server Daemon is the application server for cPanel, 
WHM, and cPanel Webmail. If it is stopped, hung, repeatedly 
crashing, or unable to bind, ports such as 2083 and 2087 will not 
respond normally.
Firewall blocks 2083 CSF, firewalld, nftables, iptables, a cloud security group, or a 
provider ACL may block TCP 2083. The service can be healthy 
locally while remote clients time out.
Source IP blocked cPHulk, CSF/LFD, fail2ban, or a manual deny rule may block only 
the client’s IP, making the incident appear user-specific.
TLS certificate problem The hostname certificate may be expired, not yet valid, 
mismatched, incomplete, or replaced with an invalid certificate. 
Browsers may stop the user before the login page loads.
DNS resolution failure The cPanel hostname or service subdomain may resolve to an old 
server, private address, Cloudflare proxy, or incorrect IPv6 address.
Apache failure - indirect Apache does not serve native 2083. However, Apache failure can 
break a proxy/service-subdomain route or create the impression of 
a broader hosting outage.
Nginx conflict - indirect A reverse proxy may intercept cpanel.example.com, use an 
incorrect upstream, bind a conflicting address/port, or present the 
wrong certificate.
Disk or inode exhaustion A full /, /var, /usr, /tmp, or inode table can prevent logs, sessions, 
temporary files, package updates, or service state files from being 
written.
Memory exhaustion / OOM cpsrvd or supporting processes may be killed or unable to allocate 
memory. Swap exhaustion and repeated OOM kills are strong 
evidence.
CPU or I/O overload Extreme load, stuck backups, malware scanning, abusive 
processes, or storage latency may cause timeouts even though the 
process exists.
Permission or package corruption Incorrect ownership/permissions or damaged cPanel files can 
produce 500 errors and failed restarts.
SELinux / security policy Unexpected enforcing policy or custom confinement may deny file, 
socket, or execute access. Confirm AVC evidence before changing 
policy.
Network or routing failure Bad route, interface problem, upstream outage, NAT error, or 
provider-level filtering can make multiple services unreachable.

3.3 Step-by-Step Troubleshooting Procedure
Step 1 - Confirm Scope and Reproduce
Test both the secure native port and any service-subdomain URL. Test from an external network and from the 
server itself. Record whether the result is timeout, refusal, TLS failure, HTTP error, or authentication failure.
# From the server
curl -kIv --connect-timeout 10 https://127.0.0.1:2083/
curl -kIv --connect-timeout 10 https://SERVER_HOSTNAME:2083/
# Basic host and route context
hostname -f
ip addr show
ip route show
Result Interpretation
127.0.0.1:2083 responds, hostname external test fails cpsrvd is likely healthy; investigate DNS, firewall, NAT, security 
group, proxy, or source-IP block.
127.0.0.1:2083 refuses No listener or immediate local reject; check service state and bind 
errors.
Local response is very slow Investigate CPU, memory, I/O wait, DNS resolver delays, or 
overloaded cpsrvd.
TLS handshake fails locally Inspect hostname certificate and cPanel TLS configuration.
Step 2 - Check cPanel Service and Process State
systemctl status cpanel --no-pager -l
ps -ef | grep '[c]psrvd'
journalctl -u cpanel --since '-30 min' --no-pager
# cPanel-native restart wrapper - use only after evidence capture
/usr/local/cpanel/scripts/restartsrv_cpsrvd
Expected result: the cPanel unit is active and a cpsrvd process exists. A failed state, repeated restart loop, 
segmentation fault, bind error, missing file, or permission denial identifies a service-level failure. If the service 
restarts successfully, immediately inspect logs to determine why it stopped rather than closing the incident as 
“fixed by restart.”
Step 3 - Verify Listening Ports
ss -ltnp | grep -E ':(2082|2083|2086|2087|2095|2096)\b'
# Fallback on older systems
netstat -lntp 2>/dev/null | grep -E ':(2082|2083|2086|2087|2095|2096)\b
A LISTEN entry on 0.0.0.0:2083 or the expected interface proves that a process has bound the port. No listener 
means the problem is below the firewall layer. A listener owned by an unexpected process indicates a port conflict 
or unsupported proxy configuration.

Step 4 - Check CSF, firewalld, nftables, and Provider ACLs
# CSF checks
csf -g 2083
grep -E '^(TCP_IN|TCP6_IN)' /etc/csf/csf.conf
csf -g CLIENT_PUBLIC_IP
# firewalld / nftables / iptables checks
firewall-cmd --list-all 2>/dev/null
nft list ruleset 2>/dev/null | less
iptables -S 2>/dev/null
ip6tables -S 2>/dev/null
The cPanel secure interface requires inbound TCP 2083; WHM normally uses 2087. If CSF is authoritative on the 
host, do not create conflicting firewalld rules. Also verify the cloud provider security group or upstream firewall, 
because a host-level allow rule cannot override an upstream deny.
Safe Firewall Change
Back up the firewall configuration, add only the required 
secure port, reload the controlling firewall, and immediately 
retest from an external client. Do not disable the firewall as a 
permanent fix.
Step 5 - Validate DNS and Hostname
hostname -f
dig +short A SERVER_HOSTNAME
dig +short AAAA SERVER_HOSTNAME
dig +trace SERVER_HOSTNAME
getent ahosts SERVER_HOSTNAME
# Compare public resolvers
dig @1.1.1.1 SERVER_HOSTNAME A +short
dig @8.8.8.8 SERVER_HOSTNAME A +short
The hostname should resolve to the server’s intended public address. A stale AAAA record can cause IPv6-
capable clients to fail even when IPv4 works. If a service subdomain is proxied through Cloudflare, test the native 
hostname and port directly to separate Cloudflare from origin service health.
Step 6 - Inspect the cPanel Hostname Certificate
openssl s_client -connect SERVER_HOSTNAME:2083 -servername SERVER_HOSTNAME </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -serial -dates -ext subjectAltName
# Refresh/check the cPanel service certificate when required
/usr/local/cpanel/bin/checkallsslcerts
Confirm that the current date is within the notBefore/notAfter range, the hostname appears in the Subject 
Alternative Name, the chain is trusted, and the certificate returned externally is the same certificate expected on 
the server. Certificate warnings alone do not prove that cpsrvd is down.
Step 7 - Check Disk Space and Inodes
df -hT
df -i
du -xhd1 /var 2>/dev/null | sort -h
du -xhd1 /usr/local/cpanel 2>/dev/null | sort -h
find /var/log -xdev -type f -size +500M -printf '%s %p\n' 2>/dev/null | sort -n

A filesystem can have free gigabytes but no free inodes, so both df -h and df -i are required. Do not delete logs 
blindly. Identify the growth source, preserve evidence, rotate or archive safely, and correct the generating service

Step 8 - Check Memory, Swap, and OOM Events
free -m
vmstat 1 5
swapon --show
dmesg -T | grep -Ei 'out of memory|oom-killer|killed process'
journalctl -k --since '-2 hours' | grep -Ei 'oom|killed process'
ps -eo pid,ppid,user,%mem,%cpu,stat,etime,cmd --sort=-%mem | head -25
An OOM entry naming cpsrvd, cPanel Perl processes, PHP-FPM, database, or antivirus processes is direct 
evidence. The final correction may require terminating a runaway process, adjusting workload concurrency, 
adding memory, tuning services, or scheduling heavy jobs outside peak hours.
Step 9 - Check CPU Load and Storage Latency
uptime
top -b -n1 | head -35
ps -eo pid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head -25
iostat -xz 1 5 2>/dev/null
pidstat -dur 1 5 2>/dev/null
Load average must be interpreted relative to CPU count and I/O wait. High load with high wa indicates storage 
contention. High sy may indicate kernel or network overhead. A single runaway backup, compression, malware 
scan, or database query can make cPanel appear unavailable without actually stopping the service.
Step 10 - Review cPanel and System Logs
tail -n 200 /usr/local/cpanel/logs/error_log
tail -n 100 /usr/local/cpanel/logs/login_log
tail -n 100 /usr/local/cpanel/logs/access_log
journalctl -u cpanel --since '-2 hours' --no-pager
tail -n 200 /var/log/messages 2>/dev/null
tail -n 200 /var/log/secure 2>/dev/null
Search around the exact failure time. Useful indicators include bind failures, certificate parse errors, “No space left 
on device,” “Too many open files,” missing Perl modules, permission denied messages, authentication blocks, 
segmentation faults, and OOM kills.
Step 11 - Check cPanel License
# Refresh the local license file after confirming public IP and entitlement
/usr/local/cpanel/cpkeyclt
# Confirm the server public IPv4 used for licensing
curl -4 https://cpanel.net/showip.cgi 2>/dev/null || true
If the license is expired, canceled, or attached to another public IP, renew or correct the license assignment, then 
refresh the local license. Do not use license refresh as a substitute for verifying port and service health.
Step 12 - Validate Package and Configuration Integrity
/usr/local/cpanel/scripts/check_cpanel_pkgs --fix
/usr/local/cpanel/scripts/upcp --force
# Run the forced update only when package corruption/version mismatch is evidenced,
# after backups and within an approved maintenance window.

3.5 Resolution and Verification
The final resolution depends on proven evidence. A representative case-study closure is shown below; it must not 
be copied as the actual RCA unless the live server produces matching evidence.
Illustrative Final RCA - cPanel
cpsrvd was active and responded on 127.0.0.1:2083, but 
remote connections timed out. CSF TCP_IN did not include 
2083 after a firewall policy change. The secure cPanel port 
was added to the approved inbound list, CSF was reloaded, 
and the client IP was removed from a temporary deny list. 
External curl and browser tests then returned the cPanel 
login page. Root cause: incomplete firewall change 
validation.
Check Action / Evidence
☐ https://SERVER_HOSTNAME:2083 opens externally without a 
timeout.
☐ The presented certificate is valid for the hostname.
☐ A test cPanel user can authenticate and load key pages.
☐ WHM on 2087 remains accessible to authorized administrators.
☐ No new cpsrvd errors appear during a 15-30 minute observation

☐ Monitoring confirms the port and process remain healthy.
3.6 Preventive Measures
 Monitor TCP 2083/2087 externally and monitor cpsrvd locally.
 Alert on disk capacity, inode use, memory pressure, swap use, OOM events, and high I/O wait.
 Use approved firewall templates and peer review for port changes.
 Track the cPanel license and public-IP changes in configuration management.
 Enable certificate-expiry monitoring for the server hostname.
 Retain and rotate cPanel/system logs; send critical logs to a remote collector.
 Document a tested break-glass SSH path before control-panel changes.

4. Issue 2 - SnappyMail (Webmail) Is Not Working
4.1 Problem Decomposition
“Webmail is not working” can describe several independent failures. The first task is to identify which operation 
fails: opening the SnappyMail URL, loading the login page, authenticating, listing mail, opening a message, 
sending a message, or receiving newly delivered mail.
Failure Stage Likely Components
URL does not open DNS, Cloudflare, firewall, Apache/Nginx, TLS, PHP-FPM, 
application files
Login page opens; login fails SnappyMail domain config, Dovecot authentication, IMAP 
host/port/TLS, account status, brute-force block
Login works; folders do not load IMAP service, mailbox permissions, quota, Dovecot indexes, 
storage I/O
Reading works; sending fails SMTP host/port/TLS/auth, Exim, routing, policy, queue
Sending succeeds; delivery delayed Exim queue, DNS, remote rejection, rate limit, reputation, full 
mailbox
Only one domain fails SnappyMail domain mapping, MX/mail host, certificate coverage, 
per-domain routing
4.2 Possible Root Causes
Potential Cause Technical Explanation
Exim stopped Users may be unable to submit outgoing mail, and inbound SMTP 
delivery may fail. This does not normally prevent the SnappyMail 
login page from rendering.
Dovecot stopped IMAP/POP3 authentication and mailbox access fail. SnappyMail 
may show login failure or connection errors even while the web 
application itself loads.
SMTP failure Wrong SMTP hostname, port, encryption, authentication method, 
firewall rule, or Exim listener prevents sending.
IMAP failure Wrong IMAP hostname/port, Dovecot listener failure, TLS problem, 
or network block prevents login and folder access.
POP3 failure Relevant only if the deployment uses POP3; SnappyMail normally 
relies primarily on IMAP for webmail.
SSL/TLS expired or mismatched The web URL, IMAP endpoint, or SMTP endpoint may present an 
invalid certificate or unsupported protocol configuration.
Wrong MX record Inbound mail is delivered elsewhere or rejected. MX does not 
control whether the SnappyMail web page loads, but it affects 
receipt of mail.
DNS error webmail.example.com, mail.example.com, or autodiscovery records 
may point to the wrong server or a proxied endpoint that does not 
support mail protocols.
Authentication failure Incorrect password, disabled account, Dovecot auth backend error, 
cPHulk/LFD block, clock issue, or username format mismatch.
Mail queue growth Outbound mail may be delayed due to remote errors, DNS failures, 
rate limiting, frozen messages, or routing issues.
Permission / quota issue SnappyMail data directory may not be writable, or mailbox 
ownership/quota may prevent Dovecot from accessing or updating 
mail.
PHP error Unsupported PHP version, missing extension, memory limit, fatal 
error, PHP-FPM pool failure, or opcache corruption can cause blank 
pages or HTTP 500.
Database issue - conditional Base SnappyMail does not require a database. A DB is relevant 
only when a plugin, address book, SSO, Nextcloud integration, or 
custom session backend is configured.
Application update/security issue Partial update, incompatible plugin, stale cache, or known 
vulnerable/outdated release may break the UI and introduces 
security risk.

4.3 Step-by-Step Troubleshooting Procedure
Step 1 - Determine Deployment Type and Application Path
First determine whether SnappyMail is a standalone PHP application, a Nextcloud integration, a hosting-panel 
plugin, or a reverse-proxied application. Paths and logs differ. Do not assume that cPanel’s native Webmail URL 
is serving SnappyMail unless the server has been explicitly customized.
find /home /var/www /usr/local -maxdepth 5 -type d -iname '*snappymail*' 2>/dev/null
ps -ef | grep -E '[p]hp-fpm|[h]ttpd|[n]ginx'
ss -ltnp | grep -E ':(80|443|143|993|25|465|587|110|995)\b
Step 2 - Test the Web Application Layer
curl -kIv https://webmail.example.com/
curl -ksS -o /dev/null -w 'HTTP=%{http_code} TIME=%{time_total}\n' https://webmail.example.com/
# Bypass public DNS/CDN and send the correct Host header to the origin
curl -kIv --resolve webmail.example.com:443:ORIGIN_IP https://webmail.example.com/
A 502/504 suggests proxy-to-backend failure. HTTP 500 suggests application/PHP failure. A redirect loop often 
indicates incorrect base URL, proxy headers, or HTTP-to-HTTPS rules. If origin access works but the public URL 
fails, focus on Cloudflare, DNS, WAF, or edge TLS.
Step 3 - Check Apache, Nginx, PHP, and PHP-FPM
systemctl status httpd --no-pager -l
apachectl configtest
systemctl status nginx --no-pager -l 2>/dev/null
nginx -t 2>/dev/null
systemctl list-units 'php*-php-fpm.service' --all --no-pager
php -v
php -m | sort

5. Issue 3 - Some Subdomains Do Not Open While the Main 
Domain Works
5.1 Why This Symptom Is Valuable
A working main domain proves that at least part of the DNS and web stack is functional, but it does not prove that 
every subdomain has a DNS record, certificate, virtual host, correct document root, or Cloudflare configuration. 
Each failing hostname must be tested independently.
5.2 Possible Root Causes
Potential Cause Technical Explanation
Missing DNS record The subdomain has no A, AAAA, or CNAME record at the 
authoritative DNS provider.
Wrong A/AAAA record The subdomain points to an old server, private address, wrong 
IPv4, or broken IPv6 address.
CNAME issue The target does not resolve, creates a loop, points across an 
unsupported proxy setup, or conflicts with another record.
VirtualHost missing Apache has no ServerName/ServerAlias entry for the hostname, so 
the request reaches a default site.
Apache configuration error Invalid include, broken user-data metadata, or failed rebuild 
prevents the expected vhost from loading.
Nginx server block missing The proxy does not contain the hostname in server_name or 
forwards to the wrong upstream.
SSL missing or wrong The subdomain is not included in a certificate, AutoSSL validation 
failed, or Cloudflare edge/origin modes are inconsistent.
Wrong document root The vhost points to a nonexistent, empty, or incorrect directory.
Permission or SELinux denial The web server cannot traverse the path or read the application 
files.
DNS propagation/caching Authoritative DNS is correct, but recursive caches still serve an old 
record until TTL expiry.
Cloudflare proxy/WAF issue Origin IP blocked, SSL mode mismatch, WAF rule, cache, or proxy 
status differs from the main domain.
Application-specific failure The vhost works, but the subdomain application returns 500, 
redirects incorrectly, or cannot reach its backend/database.

11.1 Example Closure Summary
All three reported symptoms were investigated using layer isolation. cPanel reachability was separated into local 
cpsrvd health and remote firewall access; SnappyMail was separated into web application, IMAP, SMTP, DNS, 
TLS, and quota components; and subdomain failures were separated into authoritative DNS, Cloudflare, virtual-

a specific evidence chain, a limited corrective change, end-to-end validation, and a preventive control.
12. Conclusion
Effective server troubleshooting is a disciplined evidence process, not a sequence of guesses. The engineer must 
identify the failing layer, preserve useful evidence, understand the distinction between cPanel’s cpsrvd service 
and the hosted web stack, separate webmail UI availability from IMAP/SMTP functionality, and prove DNS and 
virtual-host behavior for each subdomain independently.
The most reliable workflow is to begin with scope and local reachability, then verify service state, sockets, 
resources, logs, firewall, DNS, TLS, configuration, and the user workflow. The final fix must be supported by 
evidence, validated from multiple perspectives, and followed by an RCA that addresses the detection and process 
gaps that allowed the incident to occur.
This approach minimizes unnecessary changes, shortens recovery time, protects data and security, and produces 
documentation that another engineer can repeat. It demonstrates the Linux, cPanel, DNS, mail-server, web-
server, and logical troubleshooting skills expected from a Technical Support Engineer.
